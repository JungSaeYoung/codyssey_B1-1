| **방화벽 (firewall)** | 어떤 포트로 들어오고 나가는 통신을 허용/차단할지 결정하는 문지기. 여기서는 `ufw` 사용. |
| **계정(user) / 그룹(group)** | 리눅스는 "누가" 무엇을 할 수 있는지를 계정/그룹 단위로 관리. 한 사람이 여러 그룹에 속할 수 있다. |

## 0. OrbStack 환경 준비

OrbStack 은 macOS 위에서 Linux 가상머신을 띄워주는 무료 도구다. 도커 컨테이너처럼 가볍지만, **머신(machine) 모드**를 쓰면 systemd·sshd·cron 같은 시스템 서비스를 **진짜 서버처럼** 사용할 수 있다. 이 미션은 SSH/방화벽/cron 을 다뤄야 하므로 반드시 머신 모드로 만든다.

```bash
# macOS 호스트 터미널
brew install orbstack
orb create ubuntu:24.04 codyssey
orb shell -m codyssey         # 머신 진입
```

**한 줄씩 설명**

- `brew install orbstack` : macOS 의 패키지 매니저 Homebrew(`brew`)로 OrbStack 을 설치.
- `orb create ubuntu:24.04 codyssey` : **Ubuntu 24.04 (noble)** 머신을 "codyssey" 라는 이름으로 새로 만든다. 버전을 명시 안 하면 OrbStack 기본값(시점마다 다름)이 잡혀 22.04 가 될 수도 있어 명시 권장. (이번 미션에서 제공되는 `agent-app` 바이너리가 24.04 의 glibc/라이브러리에 맞춰 빌드돼 있음)
- `orb shell -m codyssey` : `-m` 은 "어떤 머신인지" 지정하는 옵션. 그 머신 안에 들어가 터미널을 연다. 이 시점부터는 macOS 가 아닌 **Ubuntu 안에서** 명령을 친다.

스크립트 전송 및 줄바꿈 정리 (Windows에서 작성한 경우 필수):

```bash
# macOS 호스트 — src 의 모든 .sh + bin 의 바이너리를 /tmp/ 로 한 번에
orb push -m codyssey src/*.sh bin/agent-app /tmp/

# 머신 내부 — CRLF 정리 + 실행권한
sudo apt-get install -y dos2unix
dos2unix /tmp/*.sh && chmod +x /tmp/*.sh
```

setup 7 단계는 번호 순서대로 실행하면 된다:

```bash
# 머신 내부 (sudoer 계정에서) — 한 번에
bash /tmp/00_run_all.sh

# 또는 학습 목적으로 단계별 확인
bash /tmp/01_ssh_hardening.sh
bash /tmp/02_firewall_allowlist.sh
bash /tmp/03_users_and_groups.sh
bash /tmp/04_directories_and_acl.sh
bash /tmp/05_env_and_keyfile.sh
SOURCE_DIR=/tmp bash /tmp/06_deploy_app_and_scripts.sh
bash /tmp/07_cron_schedule.sh
```

**한 줄씩 설명**

- `orb push` : macOS 의 파일을 머신 안으로 복사 (반대 방향은 `orb pull`). `/tmp/` 는 머신 안의 임시 폴더.
- `sudo apt-get install -y dos2unix` : Windows 의 줄바꿈(`CR+LF`)을 Linux 의 줄바꿈(`LF`)으로 바꿔주는 변환 도구를 설치. `-y` 는 "설치 중에 묻지 말고 Yes 로".
- `dos2unix /tmp/*.sh` : `*.sh` 모든 파일을 일괄 변환. (이걸 안 하면 bash 가 보이지 않는 `\r` 문자까지 명령 일부로 해석해서 에러난다.)
- `chmod +x /tmp/*.sh` : 해당 파일들을 "실행 가능한 파일"로 표시. (`+x` = add eXecute permission)

## 1. SSH 설정 (포트 20022 + Root 차단)

### 왜 하는가

- **SSH** 는 원격에서 서버에 접속해 명령을 칠 수 있게 해주는 표준 프로토콜이다.
- 기본 포트인 **22번**은 전 세계 해커가 봇으로 자동 스캔하는 대표 포트라, 매분 수십~수백 회 무작위 로그인 시도가 들어온다.
- 포트를 **20022 같은 비표준 번호**로 옮기면 그런 자동 공격을 대부분 회피할 수 있고, root 직접 로그인을 막아 두면 일반 계정 → `sudo` 라는 2단계를 강제할 수 있다 (= "누가" 무엇을 했는지 로그가 남는다).

### 1.1 사전 단계 — `openssh-server` 설치

OrbStack 의 Ubuntu 머신에는 SSH 서버(`sshd`) 데몬이 **기본 설치돼 있지 않다**. OrbStack 은 자체 통로(`orb shell`) 로 머신에 들어가게 해주기 때문에 표준 sshd 가 빠져 있다. 미션 요구사항(포트 20022 sshd)을 만족하려면 직접 설치해야 한다.

처음 시도 시 다음과 같이 실패할 수 있다:

```bash
$ sudo cp -a /etc/ssh/sshd_config /etc/ssh/sshd_config.bak.$(date +%Y%m%d)
cp: cannot stat '/etc/ssh/sshd_config': No such file or directory
```

→ `/etc/ssh/sshd_config` 파일 자체가 없다는 의미. SSH 서버 패키지를 먼저 설치한다.

```bash
sudo apt-get update
sudo apt-get install -y openssh-server
ls -l /etc/ssh/sshd_config    # 설치 후 파일이 생겼는지 확인
```

**한 줄씩 설명**

- `apt-get update` : 우분투의 패키지 카탈로그(어떤 프로그램을 어디서 받을 수 있는지) 를 최신화. 설치 전 관례적으로 1회 실행.
- `apt-get install -y openssh-server` : SSH 서버 데몬(`sshd`)과 설정 파일들을 설치. 설치가 끝나면 `/etc/ssh/sshd_config` 가 생기고 `ssh` 서비스가 등록된다. `-y` 는 "설치 중 묻지 말고 Yes".
- `ls -l /etc/ssh/sshd_config` : 설정 파일이 정상적으로 만들어졌는지 1줄로 확인.

### 1.2 설정 변경 명령어

```bash
sudo cp -a /etc/ssh/sshd_config /etc/ssh/sshd_config.bak.$(date +%Y%m%d)
sudo sed -i -E \
    -e 's/^#?Port .*/Port 20022/' \
    -e 's/^#?PermitRootLogin .*/PermitRootLogin no/' \
    /etc/ssh/sshd_config
sudo systemctl disable --now ssh.socket 2>/dev/null || true
sudo systemctl enable --now ssh
sudo systemctl restart ssh
```

**한 줄씩 설명**

- `/etc/ssh/sshd_config` 는 **SSH 서버의 설정 파일**. 이 파일 안의 `Port` 와 `PermitRootLogin` 두 줄을 바꿔야 한다.
- `sudo cp -a 원본 사본` : 설정 파일을 백업. `-a` 는 "권한·소유자까지 그대로 복사". 사본 이름 끝 `.bak.20260513` 처럼 날짜를 붙여 언제 만든 백업인지 표시 (`$(date +%Y%m%d)` 가 오늘 날짜로 치환됨).
- `sed` 는 **텍스트 파일을 명령어로 수정하는 도구**. `-i` = in-place(파일 자체를 수정), `-E` = 확장 정규식 사용.
  - `s/^#?Port .*/Port 20022/` 의 의미: "줄 맨 앞(`^`)이 `#` 0~1개로 시작하고 그 뒤가 `Port ` 로 시작하는 줄을 통째로 `Port 20022` 로 교체". `#?` 는 "주석 처리된 채로 있어도 풀어서 교체" 하기 위함.
  - 두 번째 `-e` 도 같은 방식으로 `PermitRootLogin no` 로 변경.
- `ssh.socket` 비활성화 : Ubuntu 24.04 는 SSH 를 "소켓 활성화" 방식으로 띄우기도 한다. 그 경우 sshd_config 의 Port 변경이 무시되므로, 소켓을 끄고 일반 서비스로만 쓰게 한다. `2>/dev/null || true` 는 "에러나도 무시하고 다음 줄로".
- `systemctl enable --now ssh` : SSH 서비스를 지금 켜고 + 부팅 시 자동 시작 등록.
- `systemctl restart ssh` : 변경된 설정을 적용하기 위해 SSH 서비스 재시작.

### 1.3 검증 (스크린샷/출력 첨부 위치)

```bash
sudo grep -E '^(Port|PermitRootLogin)\b' /etc/ssh/sshd_config
# Port 20022
# PermitRootLogin no

sudo ss -tulnp | grep -E ':20022'
# tcp   LISTEN 0  128       0.0.0.0:20022   0.0.0.0:*   users:(("sshd",pid=3245,fd=6))
# tcp   LISTEN 0  128          [::]:20022      [::]:*   users:(("sshd",pid=3245,fd=7))
```

**한 줄씩 설명**

- `grep -E` : 파일 안에서 특정 패턴을 찾는 도구 (`-E` 확장 정규식). 여기선 "줄 처음이 Port 또는 PermitRootLogin 인 줄"을 출력 → 우리가 바꾼 값이 실제로 들어갔는지 확인.
- `ss -tulnp` : 현재 시스템이 듣고(LISTEN) 있는 네트워크 포트를 보여주는 도구. 옵션 의미:
  - `-t` TCP, `-u` UDP, `-l` LISTEN 중인 것만, `-n` 이름 변환 없이 숫자로, `-p` 어느 프로세스가 쓰는지 같이 표시.
  - 결과에 `0.0.0.0:20022` 가 나오면 "모든 인터페이스의 20022 포트에서 SSH 가 대기 중" 이라는 뜻.

> **이유**: 기본 포트(22)는 자동화된 스캔/브루트포스의 1차 표적이다. 비표준 포트로 변경해 노이즈를 줄이고, root 직접 로그인을 막아 만약 자격 증명이 유출돼도 사용자 계정 단계의 사후 추적·차단 여지를 확보한다.

## 2. 방화벽 (UFW) — 20022/tcp, 15034/tcp만 허용

### 왜 하는가

- 서버는 기본적으로 "모든 포트를 열어둔" 상태일 수 있다. 필요 없는 포트가 열려 있으면 그게 곧 공격 통로.
- **UFW (Uncomplicated FireWall)** 는 우분투에서 가장 쉬운 방화벽 도구. 한 줄짜리 명령으로 "이 포트만 허용" 정책을 만들 수 있다.

### 잠깐 — 우분투에는 이미 방화벽이 있지 않나?

절반 맞는 말이다. 리눅스의 방화벽은 **3개 계층**으로 나뉘어 있다.

```
┌─────────────────────────────────────────────────────────┐
│  [사람 친화 도구 계층]                                    │
│     ufw   /   firewalld   /   iptables 직접 사용          │
└───────────────────┬─────────────────────────────────────┘
                    │ 룰을 등록
                    ▼
┌─────────────────────────────────────────────────────────┐
│  [룰셋 도구 계층]                                         │
│     iptables  (구버전)  →   nftables  (신버전)            │
└───────────────────┬─────────────────────────────────────┘
                    │ 같은 API 호출
                    ▼
┌─────────────────────────────────────────────────────────┐
│  [커널 내장 엔진]                                         │
│     netfilter   ← 패킷을 보고 통과/차단 실제로 결정       │
└─────────────────────────────────────────────────────────┘
```

- 진짜 방화벽 엔진은 맨 아래 **`netfilter`** — 리눅스 커널 안에 내장돼 있고 끌 수 없다.
- 우리가 보는 `ufw`, `iptables`, `firewalld` 는 **netfilter 에게 룰을 알려주는 입구**일 뿐 별개 방화벽이 아니다.
- 그래서 "우분투에 방화벽이 있다" = `netfilter` 는 항상 켜져 있다. 하지만 **기본 룰이 비어 있어** = "아무것도 차단 안 함" 상태. 우리가 `ufw enable` 로 한 일은 **룰을 채워 넣어 정책을 살리는 것**이다.

### 왜 `iptables` 직접 안 쓰고 `ufw` 를 쓰나

같은 정책을 두 방식으로 비교하면 직관적이다.

**`iptables` (저수준)** — 한 줄에 정보가 많고 순서가 중요:

```bash
sudo iptables -P INPUT DROP                                                  # 기본: 들어오는 거 다 차단
sudo iptables -A INPUT -i lo -j ACCEPT                                       # 루프백(자기 자신 통신) 허용
sudo iptables -A INPUT -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT  # 응답 패킷 허용
sudo iptables -A INPUT -p tcp --dport 20022 -j ACCEPT                        # SSH
sudo iptables -A INPUT -p tcp --dport 15034 -j ACCEPT                        # 앱
# ↑ IPv6 도 ip6tables 로 똑같이 한 번 더
# ↑ 재부팅 후 사라짐 → iptables-persistent 같은 별도 도구로 저장 필요
```

**`ufw` (고수준)** — 같은 일:

```bash
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow 20022/tcp
sudo ufw allow 15034/tcp
sudo ufw enable
# ↑ IPv4/IPv6 동시 적용
# ↑ 부팅 시 자동 복원
# ↑ comment 메모 내장
```

ufw 가 내부적으로 만드는 룰은 결국 첫 번째 블록과 동일하다. `sudo iptables -L -n -v` 를 쳐보면 ufw 가 깐 룰이 다 보인다.

### UFW 선택의 실제 이점

| 이유 | 설명 |
|------|------|
| **사람이 외울 수 있는 문법** | `allow 20022/tcp` 가 `-A INPUT -p tcp --dport 20022 -j ACCEPT` 보다 직관적 |
| **루프백/응답 패킷 자동 처리** | iptables 직접 쓰다 가장 많이 자기 발등 찍는 부분. ufw 는 알아서 처리 |
| **영속화 내장** | `ufw enable` 한 번이면 부팅 시 자동 적용 |
| **IPv4 + IPv6 동시** | iptables / ip6tables 따로 안 만들어도 됨 |
| **comment 메모 기능** | `ufw allow 20022/tcp comment 'SSH'` — 6개월 뒤에도 무슨 룰이었는지 알 수 있음 |
| **감사 한 줄** | `ufw status verbose` 만으로 현재 정책 전체 확인 가능 |

### 다른 선택지

| 도구 | 누가 쓰나 | 비고 |
|------|---------|------|
| **ufw** | Ubuntu / Debian | "Uncomplicated FireWall" — 이 미션의 선택 |
| **firewalld** | RHEL / CentOS / Fedora | zone(집/회사/공용) 개념 기반, 표현력 ↑ |
| **iptables** | 모든 리눅스 | 정통 도구. 풀 컨트롤 가능하지만 복잡 |
| **nftables** | 최신 커널 | iptables 후계자. ufw 도 내부적으로 점차 이전 중 |
| **클라우드 보안그룹** | AWS SG / GCP Firewall | VM *밖*에서 막음. 호스트 방화벽과 다층 방어 |

실무 패턴: **클라우드 보안그룹(1차) + 호스트 ufw/firewalld(2차)** 의 이중 방어.

> 한 줄 비유: ufw 와 iptables 는 "GUI 그래픽 카드 설정" 과 "레지스트리·드라이버 직접 편집" 의 차이 — 같은 GPU 를 다루지만 추상화 수준이 다르다.

### 미션 §2 의 실행 명령

```bash
sudo apt-get install -y ufw
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow 20022/tcp comment 'SSH'
sudo ufw allow 15034/tcp comment 'AGENT APP'
sudo ufw --force enable
sudo ufw status verbose
```

**한 줄씩 설명**

- `apt-get install -y ufw` : UFW 패키지 설치. (도구 자체가 없으면 명령을 못 쓰니까 먼저 설치)
- `ufw default deny incoming` : "**기본 정책 = 들어오는 통신은 모두 거부**". 화이트리스트 방식의 기반.
- `ufw default allow outgoing` : 나가는 통신은 모두 허용. (서버가 외부에 패키지 다운로드 등을 할 수 있어야 하므로)
- `ufw allow 20022/tcp comment 'SSH'` : 20022번 TCP만 예외로 허용. `comment` 는 나중에 정책을 봤을 때 무슨 용도였는지 알려주는 메모.
- `ufw allow 15034/tcp comment 'AGENT APP'` : 에이전트 앱이 듣는 15034번도 허용.
- `ufw --force enable` : 방화벽 활성화. `--force` 는 "정말 켤까요?" 라는 확인 질문을 건너뛰는 옵션 (스크립트화하려면 필요).
- `ufw status verbose` : 현재 적용된 규칙을 자세히 출력 → 검증용.

검증 출력 예:

```
Status: active
Logging: on (low)
Default: deny (incoming), allow (outgoing), deny (routed)
New profiles: skip

To                         Action      From
--                         ------      ----
20022/tcp                  ALLOW IN    Anywhere                   # SSH
15034/tcp                  ALLOW IN    Anywhere                   # AGENT APP
20022/tcp (v6)             ALLOW IN    Anywhere (v6)              # SSH
15034/tcp (v6)             ALLOW IN    Anywhere (v6)              # AGENT APP
```

> **이유**: "필요한 포트만 허용(allow-list)" 정책은 공격 표면을 최소화한다. UFW는 iptables/nftables 추상화로 정책을 단순 명령으로 표현·관리하기 쉽다.

## 3. 계정/그룹 생성

### 왜 하는가

- 한 서버를 여러 명이 쓸 때, **모두가 root 로 일하면 누가 뭐 했는지 추적 불가**하고, 실수로 시스템을 망가뜨릴 위험도 크다.
- 그래서 **역할별로 계정을 나누고, 권한이 필요한 그룹에만 묶어 두는 것**이 표준이다.

### 보안 원칙 두 가지

이 절의 계정·그룹 구조는 다음 두 원칙에서 출발한다.

1. **최소 권한 원칙 (Principle of Least Privilege)**
   각 계정은 **자기 역할에 꼭 필요한 권한만** 가진다. 더 많이 주면 사고 반경이 커진다. (예: QA 가 운영 키 파일을 볼 필요는 없다)
2. **직무 분리 (Separation of Duties)**
   여러 사람이 한 서버를 쓸 때 **소유자/실행자/감시자/검증자**를 일부러 분리한다. 그래야 한 계정이 털려도 피해가 격리되고, 누가 무엇을 했는지 추적이 가능하다.

### 계정 3종 — 누가 무엇을 맡나

| 계정 | 역할 비유 | 이 미션에서의 책임 | 가지면 안 되는 권한 |
| ---- | --------- | ------------------ | ------------------- |
| **`agent-admin`** | "운영자(SRE)" | • 앱(`agent-app`) 실행<br>• cron 으로 `monitor.sh` 매분 돌리기<br>• 키 파일·로그를 읽음 | **루트(sudo) 권한 없음** — 시스템 전체에 영향 주는 작업은 못 함 |
| **`agent-dev`** | "개발자" | • `monitor.sh` 같은 자동화 스크립트 작성/배포<br>• 운영 로그를 보며 디버깅<br>• 키 파일도 읽을 수 있음 (코드가 어떻게 동작하는지 확인) | **앱을 실제 실행하지는 않는다** — cron 실행자는 admin |
| **`agent-test`** | "QA / 테스터" | • 업로드 폴더에 테스트 파일을 넣어 보고 결과 확인<br>• 앱 동작을 외부에서 호출해 테스트 | **운영 키(API key)·로그를 볼 수 없다** — 운영 비밀에 접근 차단 |

> **핵심**: 세 계정 모두 **일반 계정**이다. 어느 누구도 sudo 권한을 갖지 않는다. (sudo 가 필요한 setup 은 OrbStack 의 첫 사용자 같은 별개 관리자 계정이 수행)

### 그룹 2종 — 왜 굳이 둘로 나눴나

"공유 디렉토리(업로드)" 와 "기밀 디렉토리(키·로그)" 라는 **민감도가 다른 두 자원**이 있기 때문이다. 같은 그룹 하나로 묶으면, 업로드 폴더에 접근 가능한 사람이 키 파일까지 자동으로 보게 된다.

```
                     ┌────────── 업로드 폴더 ──────────┐
agent-common  ───→  │ admin, dev, test 가 모두 R/W 가능 │
                     └─────────────────────────────────┘

                     ┌──── 키 / 로그 폴더 ────┐
agent-core    ───→  │  admin, dev 만 R/W 가능 │
                     └────────────────────────┘
```

| 그룹 | 멤버 | 의미 | 묶이는 자원 |
| ---- | ---- | ---- | ----------- |
| **`agent-common`** | admin, dev, test (3명) | "셋이서 같이 작업하는 공용 라인" | `$AGENT_HOME/upload_files` |
| **`agent-core`** | admin, dev (2명) | "민감 자원을 다루는 코어 라인" | `$AGENT_HOME/api_keys`, `/var/log/agent-app` |

### 왜 `agent-test` 는 `agent-core` 에서 빠지는가

**"Need to Know" 원칙** — 누군가 작업하는 데 굳이 필요 없는 정보는 안 보여 준다.

- QA(`agent-test`) 가 하는 일: 앱을 외부에서 호출해 결과 확인, 업로드 폴더에 샘플 파일 투입
- QA 가 안 해도 되는 일: 운영 API 키 내용 확인, 운영 로그 내용 분석
- → API 키·운영 로그는 `agent-core` 라는 좁은 그룹에만 권한을 줘서 **QA 계정이 털려도 키가 안 새도록** 함

### "그러면 왜 agent-admin 한 명한테 다 시키지 않고 dev/test 까지 나누나"

| 만약 한 계정이라면 | 실제로 일어나는 일 |
| ------------------ | ------------------ |
| "admin 하나로 다 처리" | 그 계정 비번/SSH 키가 털리면 **개발·테스트·운영 모두 동시 손상**. 또한 누가 무엇을 했는지 로그에서 구분 불가. |
| "역할별로 따로" | admin 이 털려도 **dev 의 스크립트 변경 이력**과 **test 의 테스트 흔적**은 별도. 사고 봉쇄·포렌식 가능. |

실무에서는 더 세분화해서 `agent-deploy`, `agent-monitor`, `agent-readonly` 같은 식으로 5~10개까지 나누기도 한다. 이 미션은 학습용으로 가장 작은 의미 있는 분리(3계정/2그룹)를 보여 주는 셈이다.

### cron 실행자가 왜 `agent-admin` 인가

| 후보 | 합리적인가 | 이유 |
| ---- | ---------- | ---- |
| `root` | ❌ | 모니터링은 root 권한이 필요 없다. root 로 도는 cron 작업이 많을수록 사고 반경 ↑ |
| `agent-dev` | △ | dev 는 "작성자". cron 처럼 **계속 도는 자동 프로세스의 소유자** 는 운영자(`agent-admin`) 인 게 자연스럽다 |
| `agent-test` | ❌ | test 는 `agent-core` 그룹이 아니라 `/var/log/agent-app` 에 쓸 권한이 없다 |
| **`agent-admin`** | ✅ | 운영자이면서 `agent-core` 멤버라 로그 디렉토리 쓰기 가능. monitor.sh 실행 권한도 그룹(`agent-core`)으로 확보 |

이 매핑 때문에 `monitor.sh` 가 `agent-dev:agent-core` 소유의 `0750` (소유자 rwx / 그룹 r-x / 그 외 0) 으로 배포된다. `agent-admin` 은 `agent-core` 그룹 멤버라 `r-x` 권한으로 **실행 가능**하다.

### 명령어

```bash
sudo groupadd -f agent-common
sudo groupadd -f agent-core
for u in agent-admin agent-dev agent-test; do
    sudo useradd -m -s /bin/bash "$u" 2>/dev/null || true
done
sudo usermod -aG agent-common agent-admin
sudo usermod -aG agent-common agent-dev
sudo usermod -aG agent-common agent-test
sudo usermod -aG agent-core   agent-admin
sudo usermod -aG agent-core   agent-dev
```

**한 줄씩 설명**

- `groupadd -f 이름` : 새 그룹을 만든다. `-f` 는 "이미 있어도 에러 내지 말고 그냥 넘어가라" (스크립트 재실행 시 안전).
- `for u in agent-admin agent-dev agent-test; do ... done` : bash 의 반복문. 변수 `u` 가 세 이름을 순서대로 받아 안쪽 명령을 3번 실행.
- `useradd -m -s /bin/bash "$u"` : 새 계정 생성.
  - `-m` : 홈 디렉토리(`/home/agent-admin` 같은)를 같이 만들어 줘.
  - `-s /bin/bash` : 이 계정의 기본 쉘을 bash 로. (안 지정하면 sh 가 될 수 있고 기능이 적다.)
  - `2>/dev/null || true` : 이미 있는 계정이면 에러 나는데, 그걸 무시.
- `usermod -aG 그룹 계정` : 기존 계정을 그룹에 **추가** 한다.
  - `-a` = append (기존 그룹 유지), `-G` = secondary 그룹. **`-a` 빼면 기존 그룹이 다 날아가니** 항상 같이 써야 한다.

검증:

```bash
id agent-admin
# uid=1000(agent-admin) gid=1002(agent-admin) groups=1002(agent-admin),1000(agent-common),1001(agent-core)

id agent-dev
# uid=1001(agent-dev) gid=1003(agent-dev) groups=1003(agent-dev),1000(agent-common),1001(agent-core)

id agent-test
# uid=1002(agent-test) gid=1004(agent-test) groups=1004(agent-test),1000(agent-common)
```

- `id 계정` : 그 계정의 UID, GID, 소속 그룹을 보여 준다. **기대한 그룹 3종 (agent-common / agent-core / 본인 이름) 이 다 나오는지** 확인. 단, agent-test 는 agent-core 에 속하지 않으므로 2종.

| 그룹            | 멤버                            | 의미                          |
| --------------- | ------------------------------- | ----------------------------- |
| `agent-common`  | admin, dev, test                | 공용 작업 공간 공유           |
| `agent-core`    | admin, dev                      | 비밀(키)/로그 접근 가능 코어  |

## 4. 디렉토리 구조 + ACL

### 왜 하는가

- 같은 서버 안에서도 **누구나 봐도 되는 파일**(예: 업로드 자료)과 **소수만 봐야 하는 파일**(예: API 키, 운영 로그)이 섞여 있다.
- 폴더마다 "**소유자/그룹**" 과 "**rwx 권한**"을 정해 두면 OS 가 자동으로 차단해 준다.
- 기본 권한(`chmod 770` 등) 만으로 부족할 때는 **ACL** 로 "특정 그룹에 추가 권한"을 부여한다.

### ACL 이 뭔가 — 기본 권한과의 차이

#### 1) 전통적 유닉스 권한 (POSIX 모드 비트) — 한계

지금까지 본 `rwxr-x---` 같은 권한은 파일/폴더마다 **세 단위로만 표현**된다.

```
   rwx  r-x  ---
    │    │    │
    │    │    └─ 그 외 모든 사용자(other)
    │    └────── 단 하나의 "그룹"
    └─────────── 단 하나의 "소유자"
```

문제: **그룹은 딱 하나만 지정 가능**.

> "이 폴더는 `agent-common` 도 R/W 하고 싶고, `agent-readonly` 라는 다른 그룹은 읽기만 시키고 싶다" 같은 정책을 **기본 권한만으로는 표현 못 한다**.
> 또 "어떤 한 사람(예: `alice`)에게만 추가로 R/W를 주고 싶다" 도 마찬가지.

#### 2) ACL (Access Control List) — 그 한계의 해소

ACL 은 한 파일/폴더에 **여러 개의 권한 규칙을 리스트로 붙일 수 있게** 해 준다.

```
파일: api_keys/
┌─────────────────────────────────────────┐
│ 소유자(agent-admin)         : rwx       │  ← 전통 권한
│ 기본 그룹(agent-core)       : rwx       │  ← 전통 권한
│ 그 외                       : ---       │  ← 전통 권한
│ ─────────── ACL 추가 ──────────────     │
│ group:agent-core:rwx                   │  ← 그룹 X 에게 rwx
│ user:alice:r--                         │  ← 특정 사용자 alice 에게 r
│ default:group:agent-core:rwx           │  ← 신규 파일에도 자동 부여
└─────────────────────────────────────────┘
```

**"리스트" 라는 이름이 붙은 이유** — 규칙을 여러 줄로 쌓을 수 있어서다. POSIX 모드 비트는 단 한 줄(그룹·사용자 각각 하나) 이지만, ACL 은 N 명의 사용자 + N 개의 그룹 + 기본값까지 동시 표현 가능.

### 이 미션에서 ACL 이 꼭 필요했던 이유

**기본 권한 `770` + 그룹 `agent-core` 만으로 끝낼 수 있지 않나?** 라는 질문이 자연스럽다. 둘 차이를 보자.

#### 시나리오 A — 기본 권한만 사용

```bash
chown agent-admin:agent-core api_keys/
chmod 770 api_keys/        # 소유자 rwx + 그룹 rwx
```

- ✅ 현재 폴더 자체는 정책대로 동작.
- ❌ 그런데 **agent-admin 이 안에 새 파일을 만들면** 그 파일의 그룹은 agent-admin 의 primary group (= `agent-admin`) 이 되고, 권한은 `umask` 에 따라 `644` 같은 기본값. → **agent-dev 가 그 파일을 못 본다**.
- 결과: 폴더 권한은 맞는데 안의 파일은 정책 위반. 새 파일 만들 때마다 사람이 `chown`/`chmod` 를 다시 쳐야 정상화됨.

#### 시나리오 B — ACL 사용 (이 미션의 선택)

```bash
chmod 770 api_keys/
setfacl -m  g:agent-core:rwx api_keys/   # 현재
setfacl -dm g:agent-core:rwx api_keys/   # ← default ACL
```

- ✅ 폴더 자체 정책: 시나리오 A 와 동일.
- ✅ 이제부터 **그 폴더 안에 새로 만들어지는 모든 파일이 자동으로 `agent-core:rwx` 를 상속**. agent-admin 이 새 키 파일을 떨궈도, monitor.sh 가 로그를 새로 쓸 때도 정책이 깨지지 않는다.
- 결과: **"정책을 폴더에 한 번만 박아두면 영구히 유지"**.

> 핵심: 미션의 `monitor.sh` 는 **매분 새 로그 라인을 쓰고, 가끔 새 로그 파일을 로테이트**한다. 이때마다 권한이 풀리면 다음 cron 실행에서 agent-dev 가 로그를 못 보거나 다른 사용자가 로그를 훔쳐볼 수 있다. **default ACL 만이 이 자동화 환경을 무결하게 유지**한다.

### `setfacl` 명령 한 줄씩

```bash
sudo setfacl -m  g:agent-core:rwx /path
#         │   │  │
#         │   │  └─ "group:agent-core:rwx" — 'agent-core 그룹에 rwx 부여' 라는 규칙
#         │   └──── -m (modify): 기존 ACL 에 이 규칙을 추가/수정
#         └──────── sudo: 소유자/root 만 ACL 변경 가능

sudo setfacl -dm g:agent-core:rwx /path
#         │     │
#         │     └ 같은 규칙
#         └── -d (default): 이 폴더 안에 **새로 생기는 파일/폴더**에 자동 적용될 ACL 규칙
```

- `-m` (modify): 현재 상태에 즉시 적용 — 이미 있는 폴더/파일 권한.
- `-dm` (default + modify): **앞으로 만들어질 항목**에 적용 — "정책 상속" 효과.
- **두 줄을 한 쌍으로 항상 같이 쓴다.** 한 쪽만 쓰면 현재만 맞거나 미래만 맞는 반쪽짜리가 된다.

### 확인 도구 `getfacl`

```bash
sudo getfacl /home/agent-admin/agent-app/api_keys
# # file: home/agent-admin/agent-app/api_keys
# # owner: agent-admin
# # group: agent-core
# user::rwx                       ← 전통 권한: 소유자
# group::rwx                      ← 전통 권한: 기본 그룹
# group:agent-core:rwx            ← ACL: 추가 그룹 권한 (-m 결과)
# mask::rwx                       ← 그룹/추가 ACL 에 허용되는 최대 권한
# other::---                      ← 전통 권한: 그 외
# default:user::rwx               ← 신규 파일 기본값
# default:group::rwx              ← ↑
# default:group:agent-core:rwx    ← ACL 상속 (-dm 결과)  ★ 미션 요점
# default:mask::rwx
# default:other::---
```

- 한 폴더의 **현재 정책 + 미래 정책**이 한 화면에 다 보임.
- `ls -ld` 출력 끝에 `+` 가 붙어 있으면 ACL 이 적용된 상태 (예: `drwxrwx---+`).

### ACL 의 다른 활용 예시 (참고)

| 상황 | 명령 |
| ---- | ---- |
| 특정 사용자 `alice` 에게만 r 허용 | `setfacl -m u:alice:r /path` |
| 두 그룹에 다른 권한 | `setfacl -m g:A:rwx,g:B:r-x /path` |
| 룰 하나 제거 | `setfacl -x g:agent-core /path` |
| 모든 ACL 초기화 | `setfacl -b /path` |
| 다른 곳에 동일 ACL 복사 | `getfacl src \| setfacl --set-file=- dst` |

### 한 줄 요약

> **POSIX 권한** = "한 그룹에만 적용되는 단일 규칙",
> **ACL** = "여러 사용자·그룹에 동시에, 그리고 미래 파일까지 자동 상속되도록 한 규칙 리스트".
>
> 자동화(cron, 앱이 로그를 계속 쓰는 환경)에서는 **default ACL 없이는 정책이 시간이 지날수록 풀린다** — 이 미션이 ACL 을 쓰는 이유.

```bash
sudo apt-get install -y acl
AGENT_HOME=/home/agent-admin/agent-app
LOG_DIR=/var/log/agent-app

sudo -u agent-admin mkdir -p "$AGENT_HOME"/{upload_files,api_keys,bin}
sudo mkdir -p "$LOG_DIR"

sudo chown -R agent-admin:agent-common "$AGENT_HOME"
sudo chgrp -R agent-core "$AGENT_HOME/api_keys"
sudo chown root:agent-core "$LOG_DIR"

sudo chmod 750 "$AGENT_HOME"
sudo chmod 770 "$AGENT_HOME/upload_files"   # agent-common R/W
sudo chmod 770 "$AGENT_HOME/api_keys"       # agent-core ONLY
sudo chmod 770 "$LOG_DIR"                   # agent-core ONLY
sudo chmod 750 "$AGENT_HOME/bin"

sudo setfacl -m  g:agent-common:rwx "$AGENT_HOME/upload_files"
sudo setfacl -dm g:agent-common:rwx "$AGENT_HOME/upload_files"
sudo setfacl -m  g:agent-core:rwx   "$AGENT_HOME/api_keys"
sudo setfacl -dm g:agent-core:rwx   "$AGENT_HOME/api_keys"
sudo setfacl -m  g:agent-core:rwx   "$LOG_DIR"
sudo setfacl -dm g:agent-core:rwx   "$LOG_DIR"
```

**설치하는 것**

- `acl` 패키지 : `setfacl` / `getfacl` 명령을 제공. 우분투에 기본 포함이 아닐 수 있어서 명시적으로 설치.

**한 줄씩 설명**

- `AGENT_HOME=...` : 쉘 변수 정의 (이 터미널 세션에서만 유효). 이후 `"$AGENT_HOME"` 으로 재사용해 오타를 줄인다.
- `sudo -u agent-admin mkdir -p ...` : "agent-admin 권한으로 폴더 생성". `-p` 는 "중간 폴더가 없으면 같이 만들어 줘". 중괄호 `{a,b,c}` 표현은 한 번에 여러 폴더를 만드는 bash 의 약식 문법.
- `chown 소유자:그룹 경로` : 파일/폴더의 소유자와 그룹을 변경. `-R` 은 재귀(하위 전체).
- `chgrp 그룹 경로` : 그룹만 변경 (소유자는 그대로).
- `chmod NNN 경로` : 권한 변경. 세 자리 숫자의 의미는:

  | 자릿수 | 누구 | 4=읽기 + 2=쓰기 + 1=실행 |
  | ------ | ---- | ------------------------- |
  | 1번째 | 소유자(owner) | |
  | 2번째 | 그룹(group) | |
  | 3번째 | 그 외(others) | |

  - `770` = 소유자 rwx, 그룹 rwx, 그 외 0 (= 아무 권한 없음). 비밀 폴더에 적합.
  - `750` = 소유자 rwx, 그룹 r-x (읽기·실행), 그 외 0. 실행 파일이 들어가는 `bin` 폴더에 적합.

- **ACL 부분** :
  - `setfacl -m g:그룹:rwx 경로` : 그 폴더에 "이 그룹은 rwx 가능" 이라는 규칙을 추가.
  - `setfacl -dm g:그룹:rwx 경로` : **`-d` 는 default** — "앞으로 이 폴더 안에 새로 생기는 파일도 같은 규칙을 자동 상속". 이게 없으면 새 파일을 만들 때마다 권한이 풀려서 보안 정책이 무너진다.

검증:

> 💡 **주의** : 일반 sudoer 계정 (예: `ashofrondol9475`) 으로 그냥 `ls -ld` 를 치면 `Permission denied` 가 뜬다. 그건 정책이 정상 동작 한다는 증거지만, 채점용 증거로는 부족하다 → `sudo` 를 붙여서 다시 확인한다.

# default:user::rwx

# default:group:agent-core:rwx
# default:mask::rwx
# default:other::---
```

- `ls -ld 폴더` : 폴더 자체의 권한과 소유자/그룹을 1줄로 표시 (`-d` 안 쓰면 안쪽 내용물이 나옴). 끝에 `+` 가 붙으면 ACL 이 적용돼 있다는 뜻.
- `getfacl 폴더` : 그 폴더의 ACL 규칙 전체를 보여 줌. **`group:<그룹>:rwx`** 줄과 **`default:group:<그룹>:rwx`** 줄이 둘 다 보여야 "현재 + 미래 신규 파일" 정책이 모두 살아 있는 것.

| 경로                       | 그룹           | 권한      | 정책                       |
| -------------------------- | -------------- | --------- | -------------------------- |
| `$AGENT_HOME/upload_files` | agent-common   | 770 + ACL | admin/dev/test 공동 R/W   |
| `$AGENT_HOME/api_keys`     | agent-core     | 770 + ACL | admin/dev만 R/W           |
| `/var/log/agent-app`       | agent-core     | 770 + ACL | admin/dev만 R/W           |

> **이유**: 협업이 필요한 자료(업로드)는 넓은 그룹에 R/W를 주고, 비밀(API 키)과 운영 흔적(로그)은 좁은 코어 그룹으로 제한한다. ACL `-d`(default) 옵션으로 **신규 파일도 동일 권한을 자동 상속** 받게 해 운영자가 권한 설정을 잊어도 정책이 유지된다.

## 5. 애플리케이션 실행 환경

### 왜 하는가

- 앱이 작동하려면 "어디에 키 파일이 있다", "어떤 포트를 쓴다" 같은 **실행 환경 정보**가 필요하다.
- 이걸 코드에 박아 넣으면 환경마다 다시 빌드해야 한다. 그래서 OS 가 모든 프로세스에 공유하는 **환경 변수**로 외부에서 주입하는 게 표준이다.

`/home/agent-admin/.bashrc` 말미에 환경 변수 추가:

```bash
export AGENT_HOME="/home/agent-admin/agent-app"
export AGENT_PORT="15034"
export AGENT_UPLOAD_DIR="$AGENT_HOME/upload_files"
export AGENT_KEY_PATH="$AGENT_HOME/api_keys/t_secret.key"
export AGENT_LOG_DIR="/var/log/agent-app"
```

**한 줄씩 설명**

- `~/.bashrc` 는 그 계정이 bash 를 새로 열 때마다 자동 실행되는 초기화 스크립트. 여기에 `export` 를 적어두면 로그인할 때마다 환경변수가 자동 세팅된다.
- `export 변수=값` : "이 변수를 만들고, 이 프로세스에서 실행하는 자식 프로세스에게도 물려줘라" 라는 뜻. `export` 없이 `A=1` 만 쓰면 현재 쉘 안에서만 쓰임.
- 변수 안에서 `$AGENT_HOME` 처럼 다른 변수를 참조 가능. 이 줄 자체를 읽을 때 값으로 치환된다.

키 파일:

```bash
echo "agent_api_key_test" | sudo -u agent-admin tee \
    /home/agent-admin/agent-app/api_keys/t_secret.key
sudo chown agent-admin:agent-core /home/agent-admin/agent-app/api_keys/t_secret.key
sudo chmod 640 /home/agent-admin/agent-app/api_keys/t_secret.key
```

**한 줄씩 설명**

- `echo "내용"` : 따옴표 안 문자열을 출력 (한 줄).
- `|` (파이프) : 앞 명령의 출력을 뒤 명령의 입력으로 흘려보냄.
- `tee 파일경로` : 입력으로 들어온 내용을 파일에 쓰면서 화면에도 출력. 왜 `> 파일` 대신 `tee` 를 쓰냐면, `>` 는 쉘이 즉시 처리해 버려 `sudo` 로 권한을 못 받기 때문. `sudo tee` 는 tee 자체가 sudo 로 실행되어 쓰기 권한을 얻는다.
- `chown 사용자:그룹 파일` : 키 파일의 소유자/그룹을 정확히 지정 (agent-admin 이 만들고 agent-core 그룹이 읽도록).
- `chmod 640` : 소유자=읽기·쓰기, 그룹=읽기만, 그 외=없음. **키 파일은 절대 실행할 일이 없으니 x 비트는 빼는 것**이 보안 관행.

앱 파일 배치 (한 번만):

`agent-app` 는 **미리 컴파일된 Linux 바이너리** 파일이다. macOS 호스트에 있는 그 파일을 머신의 실행 위치(`$AGENT_HOME`) 안으로 옮겨 줘야 한다.

> ⚠️ **OS 버전 주의** : 이 바이너리는 **Ubuntu 24.04 (noble) 전용**으로 빌드돼 있다 (의존 라이브러리/glibc 버전 차이). 22.04 머신에서는 동적 링크 실패 또는 `version 'GLIBC_2.38' not found` 등의 에러로 실행이 안 된다. 따라서 OrbStack 머신은 반드시 **`orb create ubuntu:24.04`** 로 생성한다.

> ⚠️ **중요** : 이 단계는 **`sudo` 가 가능한 관리자 계정** (OrbStack 첫 사용자, 예: `ashofrondol9475`) 에서 수행한다. `agent-admin` 셸에 들어와 있다면 `exit` 로 빠져나온 뒤 실행할 것. `agent-admin` 은 일반 계정이라 sudoers 에 등록돼 있지 않아 `sudo: Permission denied` 또는 `sudo-rs: I'm sorry agent-admin. I'm afraid I can't do that` (HAL 9000 패러디) 거절 메시지를 받는다.

```bash
# 현재 셸이 agent-admin 이라면 먼저 빠져나오기
exit          # 또는 Ctrl+D — 프롬프트가 ashofrondol9475@codyssey 로 돌아오면 OK

# 관리자 계정에서 바이너리 배치
sudo install -m 0750 -o agent-admin -g agent-common \
    /tmp/agent-app /home/agent-admin/agent-app/agent-app
sudo ls -l /home/agent-admin/agent-app/agent-app
# -rwxr-x--- 1 agent-admin agent-common ... agent-app
```

**한 줄씩 설명**

- `install -m 0750 -o agent-admin -g agent-common` : "권한 0750, 소유자 agent-admin, 그룹 agent-common 으로 복사". **바이너리는 실행되려면 `x` 비트가 필요**하므로 `0644` (실행 X) 가 아니라 `0750` 사용. (`0750` = 소유자 rwx / 그룹 r-x / 그 외 0)
- `/tmp/agent-app → /home/agent-admin/agent-app/agent-app` : 임시 폴더에서 앱 작업 폴더로 이동.

> 💡 **OrbStack 의 자동 마운트** : OrbStack 은 macOS 의 홈 디렉토리를 머신 안 `/Users/<macUser>/` 경로로 자동 마운트해 둔다. 따라서 `orb push` 없이 macOS 파일을 그대로 사용해도 된다.
>
> ```bash
> # 원본 위치 찾기
> find /Users/<macUser> -name agent-app -type f 2>/dev/null
> # 찾은 경로를 install 의 원본 인자로 그대로 사용
> sudo install -m 0750 -o agent-admin -g agent-common \
>     /Users/<macUser>/Desktop/codyssey_B1-1/agent-app \
>     /home/agent-admin/agent-app/agent-app
> ```

> ⚠️ **자주 만나는 에러**
>
> ```
> install: cannot install /tmp/agent-app to /home/agent-admin/agent-app/agent-app
> ```
> 원인 두 가지 중 하나.
> 1. **원본이 없음** — `/tmp/agent-app` 가 아직 머신 안에 없다. 위 자동 마운트 경로 사용.
> 2. **대상 폴더가 없음** — `/home/agent-admin/agent-app/` 가 안 만들어졌다. §4 디렉토리 구조 만들기를 먼저 실행.
>
> `ls -l /tmp/agent-app` 와 `sudo ls -ld /home/agent-admin/agent-app` 으로 원인을 가려낼 수 있다.

> 💡 **운영 원칙** : 미션의 보안 정책은 "**관리자 권한이 필요한 setup 은 sudoer 계정에서, 앱 실행은 agent-admin 에서**" 로 계정을 오가는 흐름이다. `agent-admin` 에게 sudo 를 부여하면 역할 분리(§3) 의미가 깨지므로 그렇게 하지 않는다.

앱 실행 (agent-admin 로 로그인 상태):

```bash
sudo -iu agent-admin
echo "AGENT_HOME='$AGENT_HOME'"     # 비어 있으면 환경변수 미로드
source ~/.bashrc                     # 필요 시 강제 로드
cd "$AGENT_HOME"
./agent-app
```

**한 줄씩 설명**

- `sudo -iu agent-admin` : "agent-admin 계정으로 로그인 셸을 새로 연다" 의 의미. `-i` = init(로그인 시 ~/.bashrc 등 초기화 파일 실행), `-u` = 어떤 사용자로. → 이 시점부터는 환경변수가 자동 로드된다.
- `echo "AGENT_HOME='$AGENT_HOME'"` : 환경변수가 비어 있으면 `AGENT_HOME=''` 처럼 나온다. 비어 있으면 다음 줄로.
- `source ~/.bashrc` : `.bashrc` 파일을 **현재 셸에 다시 읽어 적용**. 보통 `sudo -iu` 시 자동이지만, 이미 들어와 있던 셸이면 이게 필요할 수 있다.
- `cd "$AGENT_HOME"` : 작업 폴더 이동. `"..."` 따옴표를 붙이면 변수가 비어 있을 때 의도치 않게 `cd` 가 홈으로 가버리는 사고를 막을 수 있다.
- `./agent-app` : 현재 폴더(`./`)의 `agent-app` 바이너리 실행. `PATH` 에 현재 폴더가 안 들어 있어 `./` 가 필요. (있다면 그냥 `agent-app` 도 가능)

> **자주 만나는 에러 1 — 파일 못 찾음**
>
> ```
> bash: ./agent-app: No such file or directory
> ```
> 경로 한 칸이 빠진 듯한 신호. `$AGENT_HOME` 이 비어 있어 `cd` 가 사실상 `~` 로 갔을 가능성이 높다. 진단 순서:
>
> ```bash
> echo "AGENT_HOME='$AGENT_HOME'"   # 1) 비어 있는가
> tail -10 ~/.bashrc                # 2) export 라인이 있는가
> source ~/.bashrc                  # 3) 다시 로드
> echo "AGENT_HOME='$AGENT_HOME'"   # 4) 이제 채워졌는가
> ```
> `.bashrc` 에 `export AGENT_HOME=...` 줄 자체가 없으면 §5 환경변수 등록 단계가 빠진 것 → 위 "환경 변수 추가" 블록 다시 실행.

> **자주 만나는 에러 2 — 라이브러리 버전 불일치**
>
> ```
> ./agent-app: /lib/x86_64-linux-gnu/libc.so.6: version 'GLIBC_2.38' not found (required by ./agent-app)
> ```
> 현재 머신이 22.04 라는 신호. 24.04 머신에서 다시 시도해야 한다. (`orb create ubuntu:24.04 codyssey`)

> **임시 인라인 실행** (영구 등록과 무관, 1회용):
> ```bash
> AGENT_HOME=/home/agent-admin/agent-app \
> AGENT_PORT=15034 \
> AGENT_UPLOAD_DIR=/home/agent-admin/agent-app/upload_files \
> AGENT_KEY_PATH=/home/agent-admin/agent-app/api_keys/t_secret.key \
> AGENT_LOG_DIR=/var/log/agent-app \
> /home/agent-admin/agent-app/agent-app
> ```

### 부트 시퀀스 출력 (실제 출력 첨부)

```
> Starting Agent Boot Sequence...
[1/5] Checking User Account               [OK]
[2/5] Verifying Environment Variables     [OK]
[3/5] Checking Required Files             [OK]
[4/5] Checking Port Availability          [OK]
[5/5] Verifying Log Permission            [OK]
------------------------------------------------------------
Agent READY
```

각 단계가 뭘 보는지:

1. **User Account** : root 가 아닌 일반 계정으로 실행 중인지 (UID ≠ 0).
2. **Environment Variables** : 필요한 환경변수가 모두 비어있지 않은지.
3. **Required Files** : 키 파일이 존재하고 내용이 `agent_api_key_test` 인지.
4. **Port Availability** : 15034 포트를 다른 프로세스가 안 쓰고 있는지 (테스트 바인드).
5. **Log Permission** : 로그 폴더가 존재하고 쓰기 가능한지.

LISTEN 확인 (다른 셸에서 — 현재 셸은 앱이 점유 중):

```bash
sudo ss -tlnp | grep 15034
# LISTEN 0  16  0.0.0.0:15034  0.0.0.0:*  users:(("agent-app",pid=XXXX,fd=3))
```

- 위에서 본 `ss` 옵션과 동일. `sudo` 를 붙이지 않으면 `users:(("agent-app", ...))` 부분이 안 보인다 (다른 사용자의 프로세스 정보 조회는 root 권한 필요).

> **이유**: 환경 변수로 경로/포트를 외부 주입하면 코드 변경 없이 환경별(dev/stg/prd) 재현이 가능하고, "실행 환경을 코드로 고정"하지 않아 운영 유연성이 확보된다.

## 6. monitor.sh 배포 & 실행

### 왜 하는가

- 운영 중에는 "지금 앱이 살아 있나? 포트는 열려 있나? CPU/메모리/디스크 여유 있나?" 를 주기적으로 확인해야 한다.
- 사람이 매번 보는 건 비효율이므로 **쉘 스크립트로 자동화** → cron 으로 매분 실행 → 로그 누적 → 사후 분석.

```bash
sudo install -m 0750 -o agent-dev -g agent-core \
    /tmp/monitor.sh /home/agent-admin/agent-app/bin/monitor.sh
sudo ls -l /home/agent-admin/agent-app/bin/monitor.sh
# -rwxr-x--- 1 agent-dev agent-core 7407 May 13 21:32 /home/agent-admin/agent-app/bin/monitor.sh
```

**한 줄씩 설명**

- `install` 은 단순한 복사가 아니라 "**복사하면서 권한·소유자·그룹을 한 번에 세팅**" 해주는 명령.
  - `-m 0750` : 권한 750 (rwx r-x ---) 로.
  - `-o agent-dev` : 소유자 지정.
  - `-g agent-core` : 그룹 지정.
  - 마지막 두 인자는 `원본 대상`.
- `cp` 로 복사 후 따로 `chmod/chown` 하는 것과 같지만 한 번에 처리 → 실수 확률 ↓.
- `ls -l 파일` : 파일의 권한/소유자/그룹/크기/날짜를 한 줄로 표시. 결과의 `-rwxr-x---` 가 750 임을 의미.

> 💡 **`0750` vs `750` — 앞의 `0` 은 왜 붙이나**
>
> 결과적으로 `chmod 750` 과 `chmod 0750` 은 **완전히 같은 권한**을 만든다. 다만 권한 모드는 사실 3자리가 아니라 **4자리**다.
>
> ```
>    0   7   5   0
>    │   │   │   │
>    │   │   │   └─ other (rwx)
>    │   │   └───── group (rwx)
>    │   └───────── user (rwx)
>    └───────────── 특수 비트 (setuid / setgid / sticky)
> ```
>
> 맨 앞 1자리가 가질 수 있는 값:
>
> | 값 | 이름 | 의미 |
> |----|------|------|
> | `4` | **setuid** | 누가 실행하든 **소유자 권한으로 실행**됨 (예: `/usr/bin/passwd`) |
> | `2` | **setgid** | 디렉토리에 걸면 그 안 새 파일이 부모 그룹을 자동 상속 |
> | `1` | **sticky** | 디렉토리에 걸면 그 안 파일은 **소유자만 삭제 가능** (`/tmp` 가 1777) |
> | `0` | 없음 | 일반 파일/폴더 |
>
> 그래서 `750` 만 쓰면 시스템이 "맨 앞은 0이겠지" 라고 자동 가정하지만, **`0750` 은 "특수 비트 = 0(없음) + 권한 750" 을 명시**한 것.
>
> **`0750` 4자리 표기를 권장하는 이유**:
> 1. `4750`(setuid), `2750`(setgid), `1750`(sticky) 같은 줄과 **자릿수가 정렬**돼 가독성 ↑
> 2. "이건 8진수다" 라는 시각적 신호 — 다른 언어(Python `0o750`, Go `0750`) 와도 통일
> 3. Ansible 같은 IaC 도구는 따옴표 + 4자리(`'0750'`) 를 권장. (`750` 을 따옴표 없이 넣으면 십진수로 해석돼 권한이 깨지는 사고)
> 4. 코드 리뷰에서 "권한 의도를 이해하고 쓰는 사람" 이라는 신호
>
> 셸에서 한 줄 칠 때는 `750` 으로도 충분하지만, **문서/스크립트/자동화**에선 `0750` 4자리로 통일하는 게 관습이다.

수동 실행 (agent-admin 로):

```bash
sudo -iu agent-admin bash -lc '/home/agent-admin/agent-app/bin/monitor.sh'
```

**한 줄씩 설명**

- `sudo -iu agent-admin` : 위와 동일, agent-admin 권한으로.
- `bash -lc '명령'` : `-l` = 로그인 셸로(.bashrc 환경변수 로드), `-c '명령'` = 따옴표 안 명령 실행. → 결과적으로 "agent-admin 의 환경변수를 모두 로드한 채로 monitor.sh 를 한 번 실행".

콘솔 출력

```
====== SYSTEM MONITOR RESULT ======

[HEALTH CHECK]
Checking process 'agent-app'... [OK] (PID: 4445)
Checking port 15034... [OK]

[RESOURCE MONITORING]
CPU Usage  : 0.0%
MEM Usage  : 3.8%
DISK Used  : 1%


[INFO] Log appended: /var/log/agent-app/monitor.log
```

> 💡 **방화벽 체크의 진화 — 두 번 고친 이유**
>
> 일반 사용자(agent-admin/cron) 에서도 UFW 활성을 정확히 판별하기 위해 monitor.sh 의 체크 방식이 두 단계 진화했다.
>
> 1. **초기**: `ufw status` 명령 → root 가 아니면 거부되어 항상 WARNING
> 2. **1차 수정**: `systemctl is-active --quiet ufw` → 대부분의 환경에서 정확
> 3. **현재 (2차 수정)**: 위 + `/etc/ufw/ufw.conf` 의 `ENABLED=yes` 줄도 확인
>
> 왜 3번이 필요한가 — OrbStack 같은 컨테이너형 systemd 환경에선 **`ufw --force enable` 만으론 systemd unit 이 활성화되지 않는 경우**가 있다. 그러면 `ufw status` 는 active 로 나오는데 `systemctl is-active ufw` 는 inactive 로 잡혀 false WARNING. 설정 파일을 fallback 으로 보면 이 케이스도 잡힌다.
>
> 한편 `src/02_firewall_allowlist.sh` 와 verify_orbstack.sh §2 에선 `sudo systemctl enable --now ufw` 한 줄을 명시적으로 추가해 systemd unit 도 함께 활성화하도록 보강.

로그 누적 확인:

```bash
sudo tail -n 5 /var/log/agent-app/monitor.log
# [2026-05-13 21:33:40] PID:4445 CPU:0.0% MEM:3.8% DISK_USED:1%
```

- `tail -n 5 파일` : 파일 끝에서 5줄만 보여줌. 로그처럼 최신이 뒤에 쌓이는 파일에서 자주 사용. (반대는 `head`.)

## 7. crontab (agent-admin, 매분 실행)

### 왜 하는가

- 사람이 매분 monitor.sh 를 칠 수 없으니 **cron 데몬**(스케줄러)이 대신 실행하게 한다.
- 각 계정마다 자기만의 `crontab` 이 있어, 그 안에 "언제 + 무엇" 을 적어두면 cron 이 그 시각에 실행해 준다.

```bash
sudo systemctl enable --now cron
# Synchronizing state of cron.service with SysV service script with /usr/lib/systemd/systemd-sysv-install.
# Executing: /usr/lib/systemd/systemd-sysv-install enable cron

sudo -u agent-admin bash -c '
( crontab -l 2>/dev/null | grep -v monitor.sh ;
  echo "* * * * * AGENT_HOME=/home/agent-admin/agent-app AGENT_PORT=15034 AGENT_LOG_DIR=/var/log/agent-app /home/agent-admin/agent-app/bin/monitor.sh >> /home/agent-admin/monitor.cron.log 2>&1"
) | crontab -
'
sudo -u agent-admin crontab -l
# * * * * * AGENT_HOME=/home/agent-admin/agent-app AGENT_PORT=15034 AGENT_LOG_DIR=/var/log/agent-app /home/agent-admin/agent-app/bin/monitor.sh >> /home/agent-admin/monitor.cron.log 2>&1
```

**한 줄씩 설명**

- `systemctl enable --now cron` : cron 데몬을 "지금 켜고(`--now`), 부팅 시에도 자동 시작 등록(`enable`)".
- `crontab -l` : 현재 등록된 일정 목록 출력. `2>/dev/null` 은 "아무 일정도 없을 때 나오는 에러 메시지를 버려라".
- `grep -v monitor.sh` : "monitor.sh 가 들어간 줄은 빼고" — 이미 등록돼 있던 동일 항목 중복 등록 방지.
- `;` 으로 두 명령을 한 묶음에서 연결한 뒤 결과를 `crontab -` 에 파이프.
- `crontab -` : 표준입력으로 받은 내용을 그 계정의 crontab 으로 **덮어쓰기**.
- 등록되는 한 줄 `* * * * * 명령` 의 **5개 별표**는 "분 / 시 / 일 / 월 / 요일" 을 의미. 전부 `*` 면 "매분(모든 시각)".
- 명령 시작 부분 `AGENT_HOME=... AGENT_PORT=...` : cron 은 사용자의 `.bashrc` 를 안 읽기 때문에 환경변수를 직접 지정해 줘야 한다.
- `>> 로그파일 2>&1` : 실행 결과(표준출력)와 에러(표준에러)를 모두 같은 로그 파일에 **이어쓰기**. cron 실행에서 에러가 났을 때 어디로 갔는지 찾기 쉽다.

1~2분 뒤 로그 누적 검증:

```bash
sudo wc -l /var/log/agent-app/monitor.log     # 1분 후
# 2 /var/log/agent-app/monitor.log
sleep 70
sudo wc -l /var/log/agent-app/monitor.log     # 라인 수 증가 확인
# 4 /var/log/agent-app/monitor.log
sudo tail -n 3 /var/log/agent-app/monitor.log
# [2026-05-13 21:35:01] PID:4445 CPU:0.0% MEM:3.9% DISK_USED:1%
# [2026-05-13 21:36:01] PID:4445 CPU:1.6% MEM:3.8% DISK_USED:1%
# [2026-05-13 21:37:01] PID:4445 CPU:0.0% MEM:3.7% DISK_USED:1%
```

- `wc -l 파일` : 파일의 줄 수를 센다. 1분 전과 후의 줄 수가 늘었다면 cron 이 정상 작동하는 것.
- `sleep 70` : 70초 대기 (1분 + 여유).

> **이유**: 운영 상태는 "스냅샷이 아니라 시계열"이어야 분석 가능하다. cron으로 주기 수집을 강제하고, 로그 로테이션(10MB × 10개)으로 디스크 점유 폭주를 막는다.

## 9. (보너스 2) archive_logs.sh — 시간 기반 보존 정책

### 왜 하는가

- 매분 한 줄씩 쌓이는 로그를 영영 보관하면 디스크가 가득 찬다.
- 정책: "**오래된 건 압축해서 따로 보관, 더 오래된 건 삭제**". 디스크 절약 + 필요할 때 조회 가능.

- 7일 경과 `*.log` → `gzip` 후 `/var/log/monitor/agent-app/archive/` 로 이동
- 30일 경과 `*.gz` 삭제
- 디렉토리 미존재/권한 부족/대상 0개에서 안전하게 종료(WARNING)

```bash
sudo install -m 0750 -o agent-dev -g agent-core \
    /tmp/archive_logs.sh /home/agent-admin/agent-app/bin/archive_logs.sh

# cron (매일 03:10)
sudo -u agent-admin bash -c '
( crontab -l 2>/dev/null ;
  echo "10 3 * * * /home/agent-admin/agent-app/bin/archive_logs.sh >> /home/agent-admin/archive.cron.log 2>&1"
) | crontab -
'
```

**한 줄씩 설명**

- cron 표현 `10 3 * * *` 의 의미: "**매일 03시 10분에 실행**". 새벽 시간대를 고른 이유는 사용량이 적어 압축 작업이 운영에 거의 영향을 주지 않기 때문.
